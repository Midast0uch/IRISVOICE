## Fixed: settings-card dropdowns reverted on every click

Two real bugs in `backend/iris_gateway.py`, both confirmed by traceback in
`backend/logs/irisvoice.log` (NOT `.iris-logs/` — see "Log locations" below).

1. **`_handle_settings` (~:1204)** — `save_field_values(self._state_manager.get_state(session_id).field_values)`.
   `StateManager.get_state` is `async def` (state_manager.py:28) and was called without
   `await`, so `.field_values` hit the coroutine object → `AttributeError: 'coroutine'
   object has no attribute 'field_values'`. The exception propagated out of the handler
   and killed the `field_updated` ack that follows, so EVERY card field edit looked like
   it reverted. Fixed by awaiting it, null-guarding, and wrapping the persist in
   try/except so a disk failure can never cost the client its confirmation.

2. **TTS confirm (~:1407)** — `cfg.field_values = self._state_manager.get_field_values(session_id)`.
   **That method does not exist** on StateManager (it has `get_field_value`,
   `get_section_field_values`, `get_category_field_values`) and it was also missing
   `await`. The surrounding `except` only logged a warning, so TTS settings were
   silently never persisted. Fixed by awaiting `get_state()` and reading `.field_values`.

Verified live over a real WS (`/ws/{client_id}?session_id=...`, NOT `/ws`):
`field_update` now returns `field_updated {valid:true}`; `set_role_binding` broadcasts
`role_bindings_updated` and persists. 9 backend contract tests + 9 ModelSwitcher jest
tests pass; `tsc --noEmit` clean.

## Root cause of "socket hang up" + "have to refresh": no client-side dead-socket detection

The backend had wedged — TCP socket stayed ESTABLISHED, event loop dead, log
stopped writing for ~1h. Every endpoint (even `/docs`) timed out. Because the
socket never closed, the frontend's `isConnected` stayed **true** forever, and
every recovery path in the app keys off `isConnected` *transitions* — so nothing
re-fetched and the UI stayed stale until a manual refresh. The ModelSwitcher
"revert" was this, not a separate bug; the bind path is correct.

Fixes in `hooks/`:
- `useIRISWebSocket.ts`: added `lastFrameAtRef` (bumped in `handleMessage`, which both
  the browser and Tauri paths funnel through) + a liveness watchdog that force-closes
  the socket after 75s of total silence while connected, checking every 15s. Reconnect
  then happens through the existing onclose→scheduleReconnect path. 75s = ~2.5 missed
  heartbeats (backend pings every 30s), so a busy backend is never misjudged.
- `useInferenceState.ts`: the mount fetch was one-shot with no retry. Now retries 8×
  with linear backoff (~40s total) — the backend takes several minutes to become
  responsive on cold start, and the page is usually already open when it comes up.

## Round 2: root causes of WS disconnects + widget freeze

### My own watchdog fix was broken on the Tauri path (fixed)
`useIRISWebSocket` watchdog called `invoke('ws_disconnect')` then `connect()`.
But `connect()` only spawns a fresh Rust loop when `_sharedTauriStarted === false`
(useIRISWebSocket.ts:511), and that flag is otherwise cleared only on a full
unmount. So the Tauri branch would have killed the socket and never restarted it
— worse than the bug it was fixing. Now clears the flag first.

### Liveness detection moved into Rust (src-tauri/src/ws_client.rs)
The Rust client had NO read timeout and NO liveness check at all: on a wedged
backend `read.next()` never yields, errors, or closes, so it sat on a dead socket
forever while the frontend still reported "connected". Added a 90s
`SILENCE_TIMEOUT_SECS` arm to the message-pump `tokio::select!`; only INBOUND
frames count as proof of life (a successful write only proves the kernel took the
bytes). This belongs in Rust, not the WebView, because the two failure modes it
must survive — a frozen main thread and background-tab timer throttling — are
exactly the ones that stop JS timers. `cargo check` passes (the `stable_since`
warning at ws_client.rs:107 is pre-existing).

### Tauri tore the socket down instantly on refcount 0 (fixed) — likely the
### "disconnects frequently / always out of sync" cause
`cleanup()` branched: Tauri called `ws_disconnect` IMMEDIATELY when
`_sharedRefcount` hit 0, while the browser path deferred 2s via `_closeTimerRef`
(cancelled by `_cancelDeferredClose()` on remount). This app is a widget whose
panels mount/unmount constantly, so the refcount transiently hits 0 whenever one
closes before the next opens. Browser absorbed that churn; Taurus turned every
gap into a full teardown — dropping the `client="iris"` slot, replaying the
request_state burst, losing in-flight work. Both paths now share one 2s deferred
teardown.

### Widget freeze — leading hypothesis is memory pressure, NOT an IRIS bug
Measured: WS traffic is only ~0.2 KB/s (one 5.3 KB system_status per 30s when
idle), so a network/render flood is ruled out. RAM was 13.4/16.0 GB with
**1.1 GB in "Memory Compression"** — that is Windows actively fighting for pages
and is the tell. 20 msedgewebview2.exe processes, and the widget's are C+G
(compute+graphics, i.e. GPU-composited) per nvidia-smi. Top RAM: brave 2.2 GB,
python 1.9, WorkBuddyAI 1.5, Memory Compression 1.1, svchost 1.1, webview 1.06,
node (Next dev server) 1.0, chrome 0.6, Defender 0.4.
Under that pressure a GPU-composited webview stalls — stops painting and stops
accepting input, which is exactly "freezes or becomes unclickable".
NOT PROVEN. Wrote `.iris-logs/live/watch_gpu.py` (samples VRAM/RAM/GPU util +
webview responsiveness to gpu_watch.csv every N seconds) to confirm: if VRAM is
near ceiling at freeze time it is GPU starvation; if memory is comfortable it is
a JS main-thread block and we look at React render work instead.

## ROOT CAUSE OF THE BACKEND WEDGING (found)

The event loop shares a process with a synchronous ~30-MINUTE model load, and
that load holds the GIL nearly the whole time. Everything else follows.

### The evidence
- Wedged run: Parakeet load 08:03:35 -> 08:39:02 = **35m 27s**, then total silence.
- Current run: Parakeet load 09:01:50 -> 09:34:03 = **32m 13s**, survived.
- Measured effect: `/api/inference/state` took **6.2s during** the load vs
  **2.2s after** — the loop is starved, not deadlocked.
- `backend/audio/voice_command.py` `_do_parakeet_warm()` loads
  nvidia/parakeet-tdt-0.6b-v3 on a daemon thread, holding a
  `threading.Lock` (line 52) for the entire load.

### Why the load takes 30+ minutes (two compounding causes)
1. **The model lives on a spinning HDD.** `C:` is on DiskNumber 0 =
   TOSHIBA DT01ACA100 (MediaType=HDD). The PNY CS3030 SSD is disk1 = `D:` and
   is essentially unused. Measured sequential read of model.safetensors:
   **2.34 GiB in 30.0s = 80 MB/s** — HDD speed. `C:\dev\IRISVOICE` is on that
   same HDD, which is also why cold start is ~10 min (numpy/torch imports).
2. **Memory thrashing.** The checkpoint is 2.34 GiB fp32; materializing it plus
   the fp16 copy is ~4 GB peak, against **3.0-3.7 GB free RAM** (16 GB box,
   1.1 GB in "Memory Compression"). The working set does not fit, so the OS
   pages — on the same slow HDD. Disk is 30s of it; the rest is thrash + the
   Python-level per-tensor work the file's own comments blame for GIL starvation.

### Why this explains ALL of the reported symptoms
- Backend wedging: GIL held ~continuously for 30+ min; loop starves. TCP stays
  open, nothing is processed -> "hung but socket ESTABLISHED".
- 10-minute cold start: every import reads from the HDD under RAM pressure.
- WS "disconnects": the heartbeat loop cannot be serviced during starvation, so
  PONG_TIMEOUT (30s, ws_manager.py:30) fires and the backend drops the client.
- Widget freeze: system-wide memory + disk thrashing starves the GPU-composited
  webview (C+G per nvidia-smi).

### Fix options, ranked (NOT yet applied — need user's call)
1. `IRIS_STT_WARM_DISABLE=1` — already supported at voice_command.py:679.
   Removes the 30-35 min load from every startup; STT falls back to the
   faster-whisper path that already warms at ~08:30. One line in .env.
2. Move the HF cache to the SSD via `HF_HUB_CACHE=D:\...` (and ideally move the
   workspace itself). Biggest single win — 80 MB/s -> ~2000 MB/s.
3. Delete the stale snapshot `snapshots/7c35754d166cca382ad1e53e68b01e7c575f3a1d`
   (Jun 29, another 2.34 GiB; refs/main points at 541d1f99...). Reclaims 2.3 GB.
4. Free RAM — Brave alone is 2.2 GB across 19 processes; Chrome 0.6 GB.
5. Structural: load STT in a subprocess so the GIL contention is physically
   impossible. This is what the pre-warm delays/idle-waits are all working
   around (see the 2026-08-17 comments in voice_command.py).
