## CORRECTION to the "write URL memory at dispatch" plan (session 319)

Verified by reading the step loop and the finalize/envelope call graph:
- `_der_finalize_step` spans **14187-15670** and is the ONLY writer of both the
  envelope (call site 15276, sole call site of `_der_build_step_envelope`) and
  turn URL memory (`_der_crawled_urls` assigned only at 14278).
- The step loop reaches finalize only on success. At :8821 `if not step_success:`
  → :8830 graft-recovery route (flips success) → else :8854
  `_der_handle_step_failure` + :8858 `continue`, **skipping finalize entirely**.
  The code documents this itself at :8837-8839 ("the shared `_der_finalize_step`
  helper is only reached for successful steps").
- `_der_handle_step_failure` (:10803) builds **no** envelope (grep for "envelope"
  in 10803-12190 returns only an unrelated comment at 12079).

Consequence: a failed/crashed step produces **neither** an envelope **nor** URL
memory. So "move it into the envelope" alone does not fix the error path — the
container is not the problem, the timing is. Also, spec AC2.1 ALREADY requires an
envelope LINE for "EVERY settled step INCLUDING failures", so this is an
implementation defect against an existing AC, not new scope.

Limit on my earlier proposal: at dispatch time the kernel knows the QUERY, not the
addresses — `crawler_query` resolves seeds inside the crawler. Addresses are only
knowable from returned text (`--- Source:` / `--- Attempted:` / `--- Dead:`).
Correct fix = (a) build the envelope on BOTH success and failure paths so a
partially-reporting crawler still contributes its URLs, plus (b) record the
dispatch action itself (tool+params+query) for the total-crash case — the crawl
budget already does exactly this at :13424-13436, it is just not wired into the
exclusion set.

## Recovery lane + synthesis speed — second pass (session 319, read-only)

### The VLM lane is doubly blocked, and is NOT actually async
- `_der_maybe_open_recovery` is called at **15355, inside `_der_finalize_step`**
  (14187-15670). So recovery is only ever *considered* for steps that reach
  finalize — i.e. successful ones. A step that genuinely FAILS (crash/error)
  skips finalize entirely, so it is never a recovery candidate at all.
- Combined with the zero-sources gate (:5339), the lane can never fire on a real
  blocker: a blocker that fails the step never reaches the call site; a blocker
  inside a successful crawl leaves sources present.
- Insertion is `queue.add_item(_rec_item)` (:15362) — a normal **serial** queue
  item, not a parallel lane. The comment claims "the lane never blocks the loop"
  but that is ordering (independents first), not concurrency. Spec Decisions-Locked
  line 18 and AC9.6 promise the brain never waits on recovery; the implementation
  does not deliver that.

### Recovery budget
- `RECOVERY_DEPTH = 2` (der_constants.py:308) is **consumed nowhere** — grep finds
  only the definition. The depth limit does not exist.
- `RECOVERY_PAGE_BUDGET = 5` IS real: applied as `seed_urls[:5]` + `max_pages=5`
  (:13321-13329). The recovery step already inherits a crawl-family deadline
  (150s), so a time bound exists — the page cap is a redundant second limit.

### Final-answer speed
- Transport supports streaming (`_stream` at transport.py:603 and :968, with
  `chunk_callback`; `chunk_callback` also at 320/523/924).
- `_synthesize_response` (:15969) calls `router.generate(...)` at :16053 with
  **no chunk_callback** → the whole answer is generated before the user sees
  anything. No streaming anywhere in the DER path 14500-16100.
- `_stream_and_collect` (:2839) is defined and **never called**.
- `_generate_response` (:15902) is a deterministic formatter (no LLM), not the
  research-turn synthesis path.
- So "good answer AND speed" is achievable: wire the existing streaming path +
  shrink the prompt via the envelope (REQ-2/REQ-8). Deadline becomes a safety
  net, not the primary mechanism.
