## ROOT CAUSE of "loading percentage never reaches 100%" — FOUND

`_parse_load_progress` (line 2206) is effectively DEAD against the build actually in use.
Replayed the real parser over real production-flag logs: **43 log lines -> exactly 1 progress
event emitted, at 98%.** Nothing else matched. Two independent causes:

1. **100% is never emitted.** Line 2274 hardcodes the ready phase at `pct: 98`
   (`return {"phase": "ready", "pct": 98, ...}`). There is no subsequent 100% event. The user has
   literally never seen 100 because it does not exist in the code.

2. **The parser's patterns target log lines the server never prints at default verbosity.**
   The manager passes no `-lv`/`--verbosity`, so llama-server logs at verbosity 3, which omits
   ALL `load_tensors` / `llama_model_loader` lines. PrismML's line shapes also differ from the
   stock/ik_llama.cpp shapes the regexes assume:
     - parser wants `llama_model_load` + loading/metadata/arch -> PrismML prints
       `srv load_model: loading model '...'` (no `llama_model_load` substring) -> NO MATCH
     - parser wants `llama_model_loader: - tensor N:` -> never printed at any level -> NO MATCH
     - parser wants `llama_new_context_with_model` -> not in PrismML output -> NO MATCH
     - only `server is listening on ...` matched -> 98%
   Also `- CUDA0: ... (8191 MiB, 7114 MiB free)` lacks the literal "VRAM", so even the 5% init
   event never fires.

### The fix (verified available at -lv 4 / -lv 5)
Passing `-lv N` makes the needed lines appear. Measured on LFM2.5-VL-450M:

| level | log lines | useful progress lines |
|---|---|---|
| default (3) | ~12 | none |
| `-lv 4` | 186 | `llama_model_loader: loaded meta data with 39 key-value pairs and 148 tensors`, `print_info: n_layer = 16`, `load_tensors: offloading 15 repeating layers to GPU`, `load_tensors: offloaded 17/17 layers to GPU` |
| `-lv 5` | 1031 | adds per-layer: `D load_tensors: layer N assigned to device CUDA0, is_swa = 0` (one per layer) |

Fix = (a) pass `-lv 5` in `_build_server_cmd`; (b) parse `loaded meta data ... and M tensors`
and `print_info: n_layer = N` for totals, `load_tensors: layer N assigned` for incremental
progress, keep `offloaded N/M layers to GPU`; (c) emit a real 100% when readiness is confirmed.

### `--fit off` is a big win and is ALREADY in place
With `--fit off` Bonsai-27B reaches `n_ctx_seq` context setup at 3.56 s and warmup at 4.04 s
(vs 17.7 s warm with `-fit on`, and 75 s+ dying when cold). Pass it in any manual test or the

## Profile n_ctx ceiling: IMPROVE it, do not REMOVE it (answered for user)

`params["n_ctx"] = min(profile_n_ctx, derived_n_ctx)` (~`:2827`) means the closed loop can only
tune INSIDE the profile's number. For TwIL-LM3 that is 32,768 of ~141,000 reachable — ~108,000
tokens of real capacity unreachable.

VERDICT: keep the CONCEPT, replace the NUMBER. The number is a guess by a profile author about
hardware they cannot see. The intent it encodes is real and worth keeping: bigger context is
slower per token, so a cap encodes a speed-vs-context preference.
Fix = turn `n_ctx: 32768` into a policy (`n_ctx_policy: "maximize" | "balanced" | "minimize_for_
latency"`), let the deriver compute the true VRAM ceiling, and let the policy pick a point on it.

ORDER MATTERS (the key insight to convey): wire the loop (T5) BEFORE loosening the ceiling. The
loop measuring real throughput is what makes an aggressive initial choice safe — it corrects
downward automatically. Loosening the cap first, with no loop, means a bad first guess goes
uncorrected for the whole session.

## FreeToken assessment (arXiv 2608.16157, submitted 17 Aug 2026)

WHAT IT IS: an edge-native MoE **serving SYSTEM** (like a local vLLM/SGLang), NOT a technique to
bolt onto llama.cpp. `uv pip install "freetoken[accel]"`, Apache 2.0, OpenAI/Anthropic-compatible
API, desktop app. Authors incl. Song Han, Ion Stoica, Matei Zaharia, Kurt Keutzer — credible.
Core: bandwidth-adaptive CPU-GPU co-execution (q* policy), LRU expert caching, semantic anchor
checkpoints for agentic state reuse, elastic VRAM reallocation between expert cache and KV.
Claims 20+ MoE models, hardware "from an 8GB laptop GPU to a single workstation GPU" — so the
user's 8 GB RTX 3070 is explicitly in scope. 35B on a laptop, 284B on a gaming desktop.

WHY NOT TO ADOPT IT NOW:
1. 12 days old. No battle-testing, no community.
2. It is a whole SECOND serving stack — new transport + lifecycle + process supervision.
3. Quant formats listed are MXFP4 / NVFP4 / FP8 / BF16. The user's entire library is GGUF
   (Q4_K_M, Q3_K_M, Q1_0, Q8_0). GGUF is NOT listed as supported. Unverified.
4. Their MoE models are small (LFM2.5-8B-A1B, gemma-4-E4B). FreeToken's wins appear at 35B-753B
   where expert offloading is MANDATORY. An 8B-A1B already fits in 8 GB VRAM, so less to gain.
5. It is a clean architectural FIT if ever adopted: it speaks the OpenAI protocol, so it would
   drop in as another OpenAICompat-shaped provider in InferenceRouter — not a rewrite.

WHAT TO DO TODAY INSTEAD — the running PrismML build ALREADY has the key capability:
  -cmoe  / --cpu-moe        keep all MoE weights on CPU
  -ncmoe / --n-cpu-moe N    keep MoE weights of first N layers on CPU
  -ot    / --override-tensor <pattern>=<buffer type>
  -sm    / --split-mode {none,layer,row,tensor}
So for LFM2.5-8B-A1B: dense layers on GPU + experts on CPU via --n-cpu-moe, freeing VRAM for
context. That is FreeToken's core idea, testable today with zero new dependencies.

ARCHITECTURAL TENSION to surface: FreeToken's thesis is "never commit to a fixed offloading
strategy; map onto resources actually available." IRIS hardcodes `n_gpu_layers = -1` ALWAYS and
REJECTS 0 with "CPU fallback is not allowed" (`:2402-2406`). That rule is right for dense models
(a CPU brain is unusably slow) but MoE is different — experts are accessed SPARSELY, so CPU
expert residency costs far less than CPU dense residency. The blanket ban may be leaving VRAM
(on the table) that MoE models could spend on context. Worth a targeted benchmark.

LFM2.5-8B-A1B-UD-Q3_K_M (24 layers, Q3_K_M, 3.67 GB, native ctx 128k), PrismML build,

```
A-all-GPU    (-ngl -1)          4072 MiB   129.20 tok/s
B-ncmoe-12   (-ngl -1 -ncmoe 12) 2634 MiB    18.76 tok/s   <- 6.9x SLOWER
C-all-cmoe   (-ngl -1 -cmoe)      890 MiB     7.06 tok/s   <- 18.3x SLOWER
```

Trade: C frees 3182 MiB. KV for this model = 2*24*32*64 = 98304 B/token = 96 KiB/token at q8_0.
So 3182 MiB buys ~33,900 extra tokens — at the cost of 129 -> 7 tok/s. Disastrous trade.

CONCLUSION: the existing `n_gpu_layers = -1` / no-CPU-offload rule is CORRECT for this hardware
(RTX 3070 8GB + i7-7700 4c + 16GB DDR4). Do NOT relax it. FreeToken's adaptive q* policy, if it
measured this box, would also conclude "all GPU" — so at 8B-A1B scale it buys nothing here.
It only earns its keep at 35B+ where the model physically cannot fit in VRAM and SOME CPU
placement is forced. Even then, extrapolating, expect single-digit to low-tens tok/s.

## ANSWERS TO OPEN QUESTIONS 7-10 (my recommendations, given to user)

**Q4 (concurrent models) — CONFIRMED BUG.** Verified: NO VRAM ledger exists anywhere. The deriver
budgets against `vram_free_gb` (`:2099`, sourced from nvidia-smi `total-used` at `:1140-1141`),
i.e. whatever happens to be free AT THAT INSTANT. There is no reservation for models that WILL
load. Failure order: brain sized first (vision not yet resident -> looks like more free VRAM),
then the separate vision server (port 18181, LFM2.5-VL-3B, ~1 GB) loads -> brain's KV cache is
sized against memory that no longer exists -> OOM mid-conversation, not at load time. This is the
same failure the session-268 comment describes (iris_gateway.py:8731-8738: "crash against ~4.9GB
free (the vision server holds ~1GB)"). `_mmproj_reserve` (~:2766) reserves for the projector
attached to THIS model, NOT for the separate vision process — so it does not cover this.
FIX: VRAM ledger. Each resident model registers its footprint; deriver budgets against
`total - ledger_total - headroom`, and reserves vision's footprint UP FRONT.

**Q3 (learn from failure) — HIGHEST VALUE OF THE FOUR.** `record_tps` fires only on successful
generation, so a failing config teaches nothing and is retried identically forever — that IS the
"signal aborted at 98%" loop the user has been stuck in. FIX: negative correction on failure, but
MUST distinguish failure modes — OOM/VRAM-exhaustion -> shrink n_ctx and retry (bounded, ~3);
any other failure (corrupt model, unsupported quant) -> mark the model unusable and stop, because
blindly shrinking walks n_ctx toward zero on a genuinely broken model. Also: never re-attempt the
exact config that just failed.

**Q1 (no GPU) — make the rejection PURPOSE-AWARE.** Keep chat/tool GPU-only (a CPU brain is
unusable for a voice assistant — that is a legitimate product stance). But honour
`resolve_device_policy` (:528-540) which ALREADY declares embedding/rerank to be CPU purposes;
the argv builder simply ignores it today. This is fixing an inconsistency, not adding a feature,
and it revives `PROFILES["eco"]` (:114) which is currently dead code. Also: for chat with no GPU,
FAIL LOUDLY with an actionable message rather than silently forcing -1.

**Q2 (seed calibration) — ship NO seeds; bias conservative and grow.** Seeds are hardware-specific
constants, which AC8 forbids. The elegant answer is asymmetry: being slightly too small costs a
little context; being too big costs an OOM or a slow model. So on an uncalibrated machine prefer a
smaller n_ctx and let the loop GROW it. Cost is one imperfect first load per machine — and the
machine bandwidth number is shared by all models, so it is paid once, not per model.
