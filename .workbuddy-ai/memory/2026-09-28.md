**The ask:** add *"Is this actually done to the depth it needs to be?"* to the Oracle for
plan/task **success criteria**, because the Brain "settles for half work / doesn't push to
over-deliver".

**Why it isn't a duplicate:** `sufficient` and `done` ask whether the objective is **COVERED**;
`depth_met` asks whether it is done to the **DEPTH** the criteria demand.

**The site** (`agent_kernel.py`, right after the `[DER] run grade:` log): the one place where the
success criteria are actually in hand, because `_goal_contract_open_facts()`,
`_goal_contract_blocked_texts()` and coverage `C` are all computed there. Statement = SUCCESS

# Part 7 — the workaround: our Oracle already IS the JEV cascade

## The paper
**JEV-as-a-Judge: Accept When Confident, Escalate When Unsure** (arXiv 2609.26550, CMU — Yubo Li,
Yidi Miao, Ramayya Krishnan, Rema Padman, 22 Sept 2026). A cheap **decision-only** judge returns a
typed verdict + label probabilities; confidence q = the largest label probability; if q clears a
threshold the verdict is **accepted**, otherwise the case is **escalated to a stronger LLM**.
Measured at τ=0.9: accepts 53.7% at 92.5% vs 93.1% for the strong model alone, for 56.8% of the fee.
Its own limits: the threshold is selected on **pilot data (96 pairs)** and *"must be validated
locally for each workload and fallback"*; *"confidence is a useful ranking signal, but it is not a
certificate of correctness"*; errors concentrate in **low-confidence** decisions.

## The realisation
Our machinery **already implements it**:
- `Noul.confident()` (`decision_engine.py:159`) is **two-sided** — `p >= τ or p <= 1-τ` — and its
  docstring names JEV outright.
- `surface_shadow.surface_bool()` (`:194`) already **accepts or escalates**: confident → the engine
  decides; otherwise → `brain_bool_fn()` decides.

My first wiring hand-rolled `noul.true(0.5)`, which **discards the escalation band**. Refactored to
call `surface_bool(..., enforced=..., threshold=IRIS_DEPTH_MET_THRESHOLD, ...)`.

**The limitation this removes:** enforcement no longer needs a fully calibrated engine (100 rows +
precision ≥0.90). The engine is never asked to be right about an uncertain case — only to **know
when it is unsure**. Much weaker requirement.

## The complete approach survey (I had only considered A and E)
- **A.** shadow-only — measures, doesn't remedy.
- **B.** hard bool gate — blunt: a wrong NO says "keep going" with **no direction**, and needs full calibration. *(superseded)*
- **C.** **the JEV cascade** — accept when confident, escalate when unsure. **THE WORKAROUND.**
- **D.** **route selection** — a second consumer in the **Choice** shape (oracle.md §6), the direct
  answer to "push for another *route*"; `recovery_strategy` already does this for failures.
- **E.** **Oracle gates, Brain authors** — cheap detection, then ONE bounded Brain call designs the
  route (the graft pattern).
- **F.** **bounded depth-pushes** (a cap like `DER_MAX_GRAFTS=3`) — without it a wrong NO loops
  forever, which is exactly what killed the TrailingDirector.

**Recommended combination: C + E + F, with D as the route vocabulary.**

## Verified
- **By construction** at τ=0.80: p ≥0.80 → engine accepts (0 calls) · p ≤0.20 → **engine alone
  rejects** (0 calls) · 0.20<p<0.80 → escalates (1 call).
- **Live:** backend restarted, model serving, one turn produced
  `Oracle decide consumer=depth_met chosen=no conf=0.543 candidates=2 scoring_latency_ms=201`
  and `.rowcount.py` went **`depth_met` 0 → 1**. The first verdict is `no` at 0.543 — *not*
  confident, i.e. squarely in the escalate band. No guessing.
- The restart also re-confirmed the **encoding fix**: `stdout reader exited` = 0, server reached
  `offloaded 31/31 layers to GPU`.

## Still to build
**D** (the `depth_route` Choice consumer) and **F** (the depth-push cap). Until then, enforcement
downgrades `pass` → `capped`, which keeps the loop alive but leaves the route to the existing
graft/continuation machinery.

# Session 365 (continued) — `depth_route` SOLVED and IMPLEMENTED

**My earlier "BLOCKED" verdict was wrong, and the fix was to look one level up.** I had scored
`depth_route` at the *depth push* alone, where the incumbent does exactly one thing → a constant
`brain_choice` → §14.1's "manufacture agreement" trap. But the push is not a decision point: it is
one of **four returns inside the continuation decision** `_der_plan_next_step`. The incumbent
genuinely chooses among `cover_open_fact` (a required fact is open) · `bonus_ceiling` (C=1.0, no
bonus run, uncovered ceiling facts) · `deepen` (covered but the depth bar not met) · `finalize`.
So the reference **varies with state**, the row is scoreable by the EXISTING reader (name vs name),
and no reader change or new event type is needed.

**Implemented** (`tool_decision.py` + `agent_kernel.py`): `_DEPTH_ROUTES` = the incumbent's own
branch names + `ToolDecisionBox.depth_route(...)` modelled on `recovery_strategy` (self-registering
ConsumerSpec, `eng.decide`, row with `chosen` + `brain_choice`), wired at four sites in
`_der_plan_next_step` via a pure observer `_der_note_depth_route(route)`.

**The design decision worth keeping: each branch passes its OWN literal route name.** Predicting the
route from state would duplicate `_goal_contract_bonus_pass`'s conditions (whose only mutation is
