You are right that the ingredients are there. Memory, a tool bridge, a typed error system, Oracle, the task card, a steering inbox: all of it exists and most of it works. The execution side fails because of the shape the parts are arranged in, plus about fifteen small defects that each block coding work on their own.

The picture in one paragraph

Today a coding task runs like a relay race where each runner only sees a slip of paper. The planner writes goals on index cards. It never sees the tools. A quick sorter (Oracle) picks one tool per card from a menu of four. A small 2.6B model fills in the tool form, and the form holds only 500 tokens. A clerk then stamps "verified" if the machine did not jam, even when the test it ran failed. The next runner gets 400 characters of what happened. Nobody sees the whole job, and nobody reads the test result.

Agents that do long coding tasks well work like one skilled worker at a bench. The worker sees the whole job and picks any tool. The worker reads the real output and keeps going until the tests pass. IRIS already has that worker (_respond_direct). It is only allowed three rounds, and only for messages that a keyword list decides are "simple".

Why it breaks now

The loop was shaped for web research: gather, check, summarize. Its guards were built for that job. They include the repeat guard, the 400-character evidence limit, the text-similarity check and the "enough found" gate.

Coding is a feedback loop: read, edit, run, read the error, edit again. Every research guard pushes against that loop.

What fixes it

Keep one engine, and change what runs inside a node. DER-DAG stays the planner and the map: it builds the graph, branches into sub-loops and folds results back. Today a node is one tool call. In the new design, each node runs a small work loop: one model with all tools, a transcript for that node, and real results, until the node's goal is met.

A simple task is a graph of one node. Research and coding are the same engine with different tools. Oracle scores the choices alongside, and the task card shows the graph.

The structural problems

1. Too many places guess what you want

Seven separate parts each try to decide the kind of request:

  • the keyword gate
  • TaskClassifier
  • ModeDetector
  • _decide_mode (by message length)
  • _should_skip_der
  • Oracle's mode consumer
  • the Reviewer

They can disagree, and nothing settles which one wins. The fix is one router that makes one choice, and node loops that need no further guessing.

2. Oracle is at the wrong place in the coding loop

Oracle does its job well: it gives fast, calibrated answers over a small menu. Choosing the next action in a coding task is a different kind of question:

  • The right tool depends on the last output.
  • The menu is 4 tools, in registry order, with vision tools first.
  • The goal is cut to 200 characters, and each tool description to 90.
  • Oracle's own doc reports tool_choice AUROC as 0.54. That is chance level.

Recommendation:

  • Keep Oracle for the questions it answers well: mode, web intent, presentation and recovery hints.
  • Take it off the deciding path inside a node loop.
  • Let it score every tool choice the model makes as a shadow row. You get calibration data for free on each step, and no call waits for it.

3. Errors become answers

Many failures return a string instead of raising: "[IRIS error] …", "Still working on your previous request", "Web search is currently disabled". These strings then flow through the normal reply path:

  • They are shown as assistant replies.
  • They are stored in memory.
  • They can be spoken with the previous turn's speech line, because _last_spoken_text is reset only on the success path.

Across 527 broad except blocks, the usual pattern is "log a warning and carry on". Several consumers were dead for whole sessions because of a swallowed NameError.

4. The kernel is too large to reason about

  • One class has about 300 methods.
  • About 900 lines are dead code: plan_task, _generate_response and _handle_control_codes have no callers.
  • Comments promise behaviour that does not exist: "falls back to ReAct" appears three times, and no such fallback exists.
  • There are two IRISGateway classes.

A new agent that works in this file cannot keep the whole file in its context. That is one reason each fix breaks another part.

One engine: DER plans, every node runs a loop

The picture

DER-DAG is the general contractor. It reads the job, draws the plan, opens side jobs when it needs them (sub-loops) and collects the results (fold-back). Today the contractor hands each worker one instruction and walks away. In the new design, each node gets a skilled worker at a bench. The worker has every tool and keeps working on that node until its goal is met, then reports back. The contractor keeps the big picture, and the worker handles the details.

Why one engine is the better design, and what it costs. A separate loop would ship sooner. It would also leave two engines that drift apart, which is the exact pattern that made today's code brittle. The unified shape keeps everything DER already does well: the graph, branching, fold-back, the card contract, the ledger, the physics and Oracle rows. It replaces only the weak seam, "one node = one tool call chosen from a goal string". The cost is that the node executor must plug into the DER scheduler. That is why the executor goes in a new module with one clear entry, run_node(node, context) → NodeResult. It does not go into the 1,600-line methods.

  1. A node is a loop, not a call. Grow the ReAct loop in _respond_direct into the node executor. Inside a node, the model sees its own earlier tool calls and their results word for word. The node ends when the model returns no tool call, or when the node's token or time budget runs out. A round count does not end it. A simple chat turn is a graph with one node, so there is one engine for everything.
  2. The model can change the graph. A plan_update tool (the model's to-do list) adds, splits or closes nodes in the DAG. It uses the graft and amend paths DER already has. Each node is a matrix row: the backend creates it and orders it with seq, so the TASK_CARD contract you already built still holds. The planner also sees the tool families, so its nodes match what the tools can do.
  3. Research guards become tool policies. The repeat guard, the wall ledger and the "enough found" gate attach to the web tool family, not to the loop. Research keeps its protections, and coding is no longer blocked by them.
  4. Real coding tools.
    • read_file with line numbers and a range
    • edit_file with an exact, unique match
    • write_file for new files
    • grep and glob
    • run_command with a timeout set per call (up to 10 minutes) that returns the exit code, stdout and stderr

    Two guards apply: the agent must read a file before it edits it, and the tools stay inside the workspace folder.

  5. Checks based on what really happened. A non-zero exit code is a failure, and the model sees it. When tests were run, "done" means the last test run passed. Text similarity stays for research answers only.
  6. Memory where it pays off. Recall runs once at the start, as one bounded pack. A recall tool lets the model ask for more. At the end of the turn, IRIS saves a short trace: the goal, the files touched, the commands and the outcome. Today only the final spoken line is saved, so the next session cannot learn what was done.
  7. Long tasks. Nodes keep each transcript small, because a node sees its own work plus short summaries of the nodes before it. When a node's transcript gets close to the window, older tool output is summarized. The graph and the node results are saved to disk after each node, so a task can resume. Steering text from your existing inbox enters the running node as a user message.
  8. One error policy. Inside a node, an exception becomes a typed tool result that the model can react to, using the FAULTLINE shape you already have. Outside the loop, it becomes a turn error that the UI shows. The loop has no silent pass.

The reply surface

The picture

Today one reply is carried by three couriers, in three envelope sizes, with no delivery receipt. The front desk (the chat view) guesses which envelopes belong together. It guesses by matching turn ids as strings. When a guess fails, a card lands in the "orphan" pile, or a reply ends up in the wrong conversation.

Backend: one turn protocol

Every turn becomes turn.start, then numbered turn.part events, then exactly one turn.end. The event types are:

  • text and reasoning deltas
  • tool_call and tool_result
  • todo
  • card and document
  • error

turn.end carries a status (ok, error or cancelled) and the text to speak. The schema lives in one Python module, and the TypeScript types are generated from it. Contract tests run on both sides.

What this removes:

  • the three shapes of text_response
  • the chat_message/text_response split between the text path and the voice path
  • the flat-or-nested tolerance code
  • the chat_reasoning and error events that nothing reads

Frontend: one turn store

Build replies the way the task card is already built. Use an external store with a reducer (the same pattern as useTaskProgress) that holds Turn { id, conversationId, status, parts[] }. Then split chat-view.tsx into ChatShell → Timeline → TurnView → PartView, with one view for each part type. Specific bugs this closes:

  • The card-anchor early return. The turn id is added at line 1290 and checked at line 1293, so a card falls to the orphan pile.
  • The 500-character clamp while a reply streams. The reply freezes at 6 lines, and the element remounts.
  • Chunk, text and plan events are written to the active conversation, not to the conversation named in the event.
  • The suggestion-pill send has no conversation_id, no typing state and no dev routing.
  • The retry calls fetch inside a state updater, and it leaves a "Retrying…" message that nothing removes.
  • Backend errors and live reasoning have no listener, so you never see them.

Speech

  • Make "spoken ⊆ visible" true. Today IRIS speaks lines such as "Sub-task done; folding back into the main thread." Your own planner prompt forbids that kind of line, and the chat never shows it.
  • Use one function that decides the spoken text, not five.
  • Filter code out of speech once, on the complete text, not per sentence.

Addendum 2026-10-02 · Browser control and vision

The picture in one paragraph

The owner's goal: a user never needs another browser, because IRIS ships one. The parts exist. The agent has browser tools (browser_open, browser_observe, browser_act, browser_explore), a click-safety gate, a cursor overlay, a live takeover view and a local vision model (LFM2.5-VL-3B). But the parts are not connected into one working path. Two live runs on 2026-10-02 (open Wikipedia, search "Mount Kilimanjaro", report its height) both failed, and the vision model did not take part in either. A trace of the whole pipeline found the reasons below. Think of a car with a good engine and good wheels and no drive shaft between them.

Decisions so far

1. Model:

The app stays model-agnostic. Testing uses gemma4:31b-cloud on Ollama, with larger models later. The Cline pass key is available when needed. Result: the Ollama transport must carry tools (B1).

Split roles stay: a fast local 2.6B model for tool calls next to an API Brain. In a node, the tool model is the hands. It makes valid calls, repairs schema errors locally and gives the Brain a digest of large output. The Brain is the pen. Fields marked authored_by: "brain" (write_file.content, edit_file.new, create_artifact.content) are written by the Brain in a streamed call and passed straight into the tool call. The 500-token limit (B2) therefore never cuts a file. The reply surface report has the details.

2. Oracle:

It advises and records shadow rows in the node loop, and it keeps deciding where its bar says it may.

3. Engine:

One engine. DER-DAG plans and branches, and every node runs a bounded work loop. Developer mode changes over first, then personal-mode research.

4. Developer view:

The live execution matrix, grown from your cli-preview Blueprint concept, with chevrons at the frame and row levels and a one-line thought stream. The visual details stay open for a design pass.

5. Browser and vision (2026-10-02):

The web toggle is the only gate on browser use, in both modes. The local vision model is the fallback for a Brain or tool model that cannot see; a model that can see does the work itself. The fallback ladder is the ordered list of vision models to auto-load, and an empty ladder uses the vision card's pin. Two local models at once is a separate spec. Goal: the user never needs another browser.
