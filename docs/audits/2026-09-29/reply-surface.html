You are right that the task card and the prism card could make a very clean experience together. Three things stop that today. The rule for "text or card" lives in five places that disagree. The card can show up with no name. And the permission and question cards live outside the conversation, with no record left after you answer.

The picture in one paragraph

Picture a good assistant who hands you work. They tell you the answer. When they make you something to keep, such as a report, a script or a chart, they hand you a labelled folder. You never wonder which one you got. IRIS today has five clerks who each decide whether to use a folder. One clerk reads your question for keywords. One counts steps. One checks for headings, one looks for a failed web search, and one is the model itself. Sometimes they overrule each other. Sometimes the folder has no label. And the one clerk who is meant to make folders on request (the render_document tool) crashes every time.

What decides "text or card" today

The model can ask for a card through its {speak, show} JSON. Four other rules then change the result:

The rule: one trigger, stated to the model

Replace the five rules with one tool and one plain rule in the prompt. The model learns one thing, and the code does exactly that thing.

ANSWER
Plain text is the reply. It can be long, with headings, lists, tables and short code blocks. It is shown in full and never turned into a card.
ARTIFACT
Call create_artifact when you made something to keep, reuse or open on its own: a report, a file of code, a dataset, a diagram or an interactive page. Always give it a title and a one-line summary.
BOTH
When you make an artifact, the reply says in 1–3 sentences what you made and what matters about it. It never repeats the artifact's content.
SIGNS
These signs mean an artifact: the user asked for a file, report, page, chart or document; the content stands alone and is longer than about 40 lines; the user will save, share or open it again; or the content is visual. A snippet under about 15 lines stays in the answer.

Known side effect of this rule (found 2026-10-07, fixed). Teaching the reply as a literal ANSWER: label made models sometimes copy the label into the reply itself - the streamed delta, the final text and the spoken line all began "ANSWER: ..." (recorded in __tests__/fixtures/turns/recorded_personal_ok.json). The rule text is unchanged; the reply exit now strips one leading label from the display text and the spoken line (artifact_policy.strip_leading_answer_marker -> AgentKernel._finalize_response, guarded by test_answer_marker_strip_contract.py). A label mid-text is prose and stays. The label can still flash in the streamed bubble until turn.end replaces it.

Oracle's presentation consumer keeps a shadow score for every turn: "should this have been an artifact?". Where it disagrees with the model, the disagreement becomes calibration data. It never overrides the model. The {speak, show} JSON still parses for older prompts, and it converts to the same create_artifact event, so nothing breaks while the prompts change.

The artifact format

create_artifact(
  title:    str                 # required, ≤ 60 chars, shown on the card
  kind:     "document" | "code" | "data" | "diagram" | "page" | "image"
  summary:  str                 # required, one line under the title
  content:  str                 # the body; see "who writes it" below
  language: str | None          # kind=code: python, ts, rust…  kind=data: csv, json
  artifact_id: str | None       # pass it to publish a new version of an existing artifact
) → { artifact_id, version }
  • document: markdown, rendered with the one shared renderer, including mermaid blocks.
  • code: a file with syntax highlighting, a line count, and copy and save-to-workspace buttons.
  • data: CSV or JSON, shown as a sortable table with the raw view one click away.
  • diagram: mermaid or SVG, drawn full width with pan and zoom in the panel.
  • page: a complete HTML page with CSS, SVG, diagrams and JavaScript, like the two reports I made for you. See the page contract below.

The document store already handles any format string, card_id, turn_id, versions and body fetch. The backend needs few changes. Most of the work is the renderer and the prompt.

The page contract (HTML, SVG, JavaScript)

  • Isolation. Every page renders in <iframe srcdoc sandbox="allow-scripts"> with no allow-same-origin, as your dashboard browser tab already does. A page cannot read IRIS, its storage or its cookies.
  • A content policy injected by IRIS. Inline CSS and JS are allowed. Scripts load only from a short CDN allowlist (cdnjs, jsdelivr). No network requests, no forms, no top-level navigation. Images are data: URIs only.
  • Theme. IRIS injects its tokens (--iris-bg, --iris-fg, --iris-accent, the fonts), so pages match the app without extra work from the agent.
  • Size. A tiny injected script reports the page height with postMessage, so the peek fits the content. The panel shows the page at full size. "Open in browser surface" moves it to the dashboard tab.
  • Authoring guide. The page kind comes with a short guide in the prompt: self-contained, the tokens, readable on phone widths, <pre class="mermaid"> for diagrams. This is the same kind of guide I followed to build these reports.

Who writes the content when the models are split

You plan to run a fast local 2.6B model for tool calls next to an API Brain. That fits well, as long as each model does the job it is good at. The tool model is the hands: it turns a decision into a valid call and fixes schema errors locally and fast. The Brain is the pen: it writes anything long.

  • Tool schemas mark large fields as authored_by: "brain". These are create_artifact.content, write_file.content and edit_file.new.
  • The tool model fills the small fields: path, title, kind, language. For a marked field it writes a short brief instead, for example "a Python module with a Reader class that…".
  • Before dispatch, the node executor asks the Brain to write the marked field, streamed, with the node's transcript and the brief. The Brain's text goes straight into the call. The small model never copies it, so it cannot cut it off at 500 tokens.
  • The tool model can also read large tool output for the Brain. It gives back the first and last parts plus a short digest, so the Brain spends its context on decisions.

This split also applies to the node executor in the execution audit. When one model has native tool calls and a large window, the node loop can use it for both roles, and the split is an option, not a requirement.

Permission, before and after an answer

How the task card and the artifacts work together

  • The task card shows the work. It appears while the agent works. When the turn ends, it folds to one line: title, steps, time and memories used.
  • The reply is the answer. It is always text, written for you, and it names what was made.
  • An artifact is a thing you keep. It shows as a compact, named card under the reply. It is also the last row of the task card (✦ MADE), so the work and its result connect.
  • Interactions live in the turn. Permission and question cards appear where the agent paused. Each one leaves a receipt.
  • One chassis, two views. The same data drives both modes. Personal mode draws compact glass cards, and developer mode draws matrix rows. It is the same pattern as the task card and the ASCII matrix, carried through to every card type.
